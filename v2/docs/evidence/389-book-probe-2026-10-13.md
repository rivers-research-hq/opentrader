# #389 human lock — OANDA practice book: polling vs streaming (measured 2026-10-13)

The only item left on #389 is the refresh-mechanism decision. It was being asked
without a measurement on file — the probe script existed (`v2/tools/venue_book_probe.py`,
committed c15040b) but had never been run. It has now been run, read-only, against
OANDA **practice**. Raw output: `389-book-probe-raw-2026-10-13.txt`.

## Result — the decision is settled by the venue, not by preference

| Question | Measured |
|---|---|
| Is the practice orderBook populated? | **Yes.** EUR_USD 6716 buckets, USD_JPY 2439 |
| positionBook populated? | **Yes.** EUR_USD 596, USD_JPY 1229 |
| Wire shape | keys `price`, `longCountPercent`, `shortCountPercent`; **every value is a JSON string** |

## Why this closes the lock

1. **There is no streaming branch to choose.** `/v3/instruments/{i}/orderBook/stream`
   returns 404 on practice. The lock presented as "polling vs streaming" is not a
   real fork — polling is the only mechanism the venue offers. This is the same
   shape as the crypto lane's #159: an endpoint was assumed and never verified.
2. **2 s is already faster than the book moves.** Zero of three 2 s polls showed a
   change at 1M buckets. Polling faster than ~2 s buys nothing on practice; it only
   spends rate limit. A 2–5 s cadence is defensible; sub-second is not.
3. **The wire shape is confirmed.** `price`/`longCountPercent`/`shortCountPercent`
   as **strings** matches the parser already in `crates/ot-venues/src/oanda/book.rs`
   — no adapter change is required to consume this.

## Recommended resolution

Accept **polling at a 2–5 s cadence** as the ladder's refresh mechanism and drop
the streaming branch from the ticket. The remaining work is not a decision: the
venue-side fetch and the ladder model are already landed (fccfaff, eeedd8c); the
`ui_ladder` surface just needs to be wired to the poller. If a later cadence study
is wanted, re-run the probe with `--interval 0.5` and compare — the script is
re-runnable and needs no code change.

## Caveats — stated so they are not inherited as fact

* **Practice only.** These numbers are from `api-fxpractice.oanda.com`. A live
  account's book is denser and moves more; the 0/3 figure should not be quoted as
  a live-account cadence bound. The 404 is a *route* result and would be expected
  to hold, but it was measured on practice.
* **1M buckets only.** Wider buckets move less; finer buckets (`--bucket 5S`) would
  change faster. The cadence number is conditional on bucket width.
* **Four polls is a small sample.** 0/3 is a point estimate, not a rate. It is
  enough to reject "the book changes every 2 s"; it is not enough to characterise
  the change process.
